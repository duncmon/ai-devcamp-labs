Part 1

The Dual-Tier Pipeline Architecture

Production Pattern

In modern agentic systems, releasing code requires more than unit tests passing syntax checks; it requires behavioral invariants (brand voice, PII redaction, human approval gates) to be rigorously proven against stochastic judge models before reaching production traffic.

The two tiers serve distinct engineering purposes:

  • Tier 1 (Local Process Gate): Fast-feedback loop for developers during local feature branching. Directly exercises the ADK Python runtime, sidecar lifecycle, and judge models without cloud container packaging overhead.
  • Tier 2 (Cloud Build Gate): The ultimate release arbiter. Runs inside isolated Google Cloud Build containers, executing tests against clean source bundles, guaranteeing that only code satisfying all behavioral rubrics can produce a new Cloud Run or Agent Engine revision.

Part 3

The Zero-Exit Trap & Fail-Closed Defensive Parsing

Defensive Invariant

The fundamental flaw in naive CI/CD configurations is trusting the CLI exit code. In google-adk==2.4.0, the command: 

uv run adk eval backend/social_poster evals/golden.json --config_file_path evals/eval_config.json

returns exit code 0 even when test cases fail (Tests failed: 1). A pipeline that relies on set -e without manual output parsing will silently wave regressed code through to production.

The Fail-Closed Parsing Logic

In both cloudbuild.yaml and evals/deploy_with_eval_gate.sh, the output stream is piped through tee and defensively evaluated: 

FAILED=$(grep -oE "Tests failed: [0-9]+" /tmp/eval_output.log | tail -1 | grep -oE "[0-9]+")

# Check 1: Fail Closed on Unparseable or Truncated Output
if [ -z "$FAILED" ]; then
  echo "Could not parse eval result — treating as failure (FAIL-CLOSED INVARIANT)."
  exit 1
fi

# Check 2: Block on Any Regression
if [ "$FAILED" -gt 0 ]; then
  echo "Golden evalset regression: $FAILED test(s) failed. Blocking deploy."
  exit 1
fi

echo "Golden evalset passed clean."
Why "Fail Closed" Matters: If the ADK team alters the CLI summary phrasing or if the container runs out of memory mid-evaluation, FAILED will evaluate to an empty string. A naive [ "$FAILED" -gt 0 ] check evaluates false on empty strings in bash, which would inadvertently allow a broken deployment. Check 1 ensures that any ambiguity halts the release.

Part 5

Permanent Engineering Recommendations & Direnv Context Isolation

Best Practices

Why direnv is Essential in Enterprise GCP Workstations:

In enterprise Google Cloud development, engineers frequently juggle multiple active projects (e.g., personal development sandboxes, devcamp environments like ai-devcamp-duncan-395792, and production systems). Without automation, developers must manually run gcloud config set project or remember to export variables on every terminal tab switch. A single missed export can cause catastrophic context-bleeding—such as provisioning test compute against a production billing account.

The Role of direnv: By placing an .envrc file at the project root containing: 

export CLOUDSDK_ACTIVE_CONFIG_NAME="ai-devcamp"
export GOOGLE_CLOUD_PROJECT="ai-devcamp-duncan-395792"

the developer's interactive shell automatically activates the isolated gcloud profile and project context upon entering the workspace and unloads them upon leaving.

Why .envrc Must Be in .gcloudignore: Because .envrc is purely local workstation configuration (which may also contain developer-specific secrets and profile references), it must NEVER be uploaded to Google Cloud Build or containerized into Cloud Run images. Adding .envrc and *.envrc to .gcloudignore is a mandatory enterprise security rule.

The Subshell Invariant: Automated agents and CI runner subshells do not automatically evaluate directory hooks; therefore, provisioning scripts and commands must explicitly source .envrc or export these variables to prevent fallback to unintended default configurations.

  1. Mandatory .envrc in .gcloudignore: Always exclude .envrc, *.envrc, and .env* in .gcloudignore across all GCP repositories. Local direnv environments often store active configurations, project IDs, and service tokens that must never be packaged into build images.
  2. Dynamic GCP Identity Resolution: Replace hardcoded project numbers and service account emails in provisioning scripts with dynamic resolution: 
    PROJECT_ID=$(gcloud config get-value project)
PROJECT_NUM=$(gcloud projects describe "$PROJECT_ID" --format="value(projectNumber)")
CB_SA="${PROJECT_NUM}@cloudbuild.gserviceaccount.com"
  3. Decoupled Gating Scripts: Separate the gating logic from Cloud Build specifics so local developers can run ./evals/deploy_with_eval_gate.sh pre-commit before triggering expensive remote builds.
  4. Visual Console Proofs vs. Raw Logs: While raw CLI build logs (such as docs/screenshots/lab4-step6-cloudbuild-success.txt) verify command execution, production documentation requires visual UI screenshots from Google Cloud Console (Cloud Run dashboard and Cloud Build history) to prove live endpoint health and traffic allocation without ambiguity.
