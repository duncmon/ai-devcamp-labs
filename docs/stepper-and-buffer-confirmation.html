In-Flight Stepper Synchronization & The Single-Confirmation Gate

A deep architectural analysis and engineering record documenting how we eliminated subagent state progression lag in CopilotKit and prevented duplicate Human-in-the-Loop authorization prompts during Buffer MCP publishing.

Context: Following the successful integration of multimodal image synthesis (gemini-2.5-flash-image), automatic GCS persistence, and Buffer MCP dispatch, live end-to-end verification uncovered two subtle friction points: the pipeline stepper remained visually frozen on Researching while draft_agent executed, and the user was required to confirm publication twice. Here is how we systematically resolved both.

Challenge 1 · State Reactivity

The ADK Event Lifecycle Paradox & In-Flight Stage Synchronization

SSE Lifecycle
🔍 The Symptom & Root Cause

During multi-agent execution, attendees observed an unnatural visual desynchronization in the Social Spark dashboard (captured live in Figure 1):

  • In the bottom Agent Activity drawer, research_agent was marked as done, and draft_agent was actively marked as running….
  • Yet at the top of the screen, the horizontal Pipeline Stepper remained stationary on Researching. Only when draft_agent finished its entire 15-second generation waterfall did the stepper jump directly to Approval, completely skipping the visible Drafting phase.

The Architectural Mechanism: Investigating the Google ADK and ag-ui-adk event lifecycle uncovered why server-side callbacks alone could not solve this:

  • In Google ADK, before_tool_callback runs synchronously in-process. While it successfully mutates tool_context.state["pipeline_stage"] = "drafting" in memory, ADK does not emit an SSE event when a tool begins execution.
  • ADK only yields Event objects containing actions.state_delta when a tool completes and returns a FunctionResponse, or at turn boundaries when emitting a final STATE_SNAPSHOT.
  • Consequently, CopilotKit's useCoAgent({ name: "social_poster" }) hook receives zero state deltas while draft_agent is in flight, leaving state.pipeline_stage stuck on the value emitted when research_agent concluded (researching).
  • Conversely, ActivityFeed.tsx inspects useCopilotChatInternal(): as soon as the orchestrator emits a FunctionCall event, the streaming message array receives toolCalls: [{function: {name: "draft_agent"}}], allowing it to render the running state immediately.
🛠️ The Solution: Dual-Source Reactive Stage Derivation

We refactored frontend/app/components/StagePanel.tsx to read from both CopilotKit's shared state and the live streaming message feed: 

// frontend/app/components/StagePanel.tsx
function getActiveTool(messages: any[]): string | null {
  const toolResults = new Set<string>();
  for (const msg of messages) {
    if (msg.role === "tool" && msg.toolCallId) {
      toolResults.add(msg.toolCallId);
    }
  }
  for (let i = messages.length - 1; i >= 0; i--) {
    const msg = messages[i];
    if (msg.role === "assistant" && Array.isArray(msg.toolCalls)) {
      for (let j = msg.toolCalls.length - 1; j >= 0; j--) {
        const call = msg.toolCalls[j];
        if (call?.id && !toolResults.has(call.id)) {
          return call.function?.name ?? null;
        }
      }
    }
  }
  return null;
}

export function StagePanel() {
  const { state } = useCoAgent<AgentState>({ name: "social_poster" });
  const { messages } = useCopilotChatInternal();

  let current = state?.pipeline_stage ?? "idea";
  const activeTool = getActiveTool((messages as any[]) ?? []);

  // Bridge the in-flight subagent execution window
  if (activeTool === "draft_agent") {
    current = "drafting";
  } else if (activeTool === "research_agent") {
    current = "researching";
  } else if (activeTool === "memory_agent" || activeTool === "load_memory") {
    current = "consulting_memory";
  }

  const currentIdx = STAGES.findIndex((s) => s.key === current);
  // ... render stepper ...
}

Result: The instant the orchestrator dispatches draft_agent, the stepper reactively illuminates ✍️ Drafting with zero latency. When drafting concludes, the server-emitted awaiting_approval state takes over smoothly.

Challenge 2 · HITL Authorization

The Premature Tool Execution Trap & The Double Confirmation Gate

HITL Mechanics
🔍 The Symptom & Root Cause

When authorizing a post scheduled for Buffer, attendees noticed that approving the action required clicking Approve twice (evidenced by duplicate "Responded." chips and stacked adk_request_confirmation spans in Figure 2).

❌ The Double-Gate Failure Waterfall

  1. User states: "lets set this up for posting!".
  2. Orchestrator invokes create_post optimistically without channelId.
  3. ADK intercepts create_post (require_confirmation=True) → Prompts User.
  4. User clicks Approve (#1).
  5. Buffer MCP executes create_post → Fails: Missing required field: channelId.
  6. Orchestrator catches error, calls get_account & list_channels to get channel ID.
  7. Orchestrator invokes create_post with channelId.
  8. ADK intercepts create_post again → Prompts User Approve (#2)!

✅ The Single-Gate Production Standard

  1. User states: "lets set this up for posting!".
  2. Orchestrator obeys strict prerequisite: queries get_account → list_channels.
  3. Primary buffer_channel_id cached in session state.
  4. Orchestrator invokes create_post fully formed (with channelId and image asset).
  5. ADK intercepts create_post → Prompts User Approve (Once).
  6. User clicks Approve.
  7. Buffer MCP executes successfully on first attempt.
  8. Post enters Buffer queue with zero redundant gates.
🛡️ The Solution: Strict Prerequisites & Session State Caching

To eliminate the premature call, we implemented defense-in-depth across prompt engineering, state caching, and tool callbacks:

  • Orchestrator Mandate: Updated _BUFFER_CHANNEL_LOOKUP and root_agent.instruction with a mandatory operational invariant: 
    MANDATORY BUFFER CHANNEL PRE-REQUISITE:
Buffer's create_post REQUIRES a valid channelId. Calling create_post without channelId will fail immediately.
BEFORE calling create_post, you MUST resolve the channelId yourself:
  1. Call get_account (no arguments) to find organizationId.
  2. Call list_channels with that organizationId.
  3. Pass that channel's id as channelId in create_post. NEVER call create_post before list_channels.
  • Channel ID Caching in _track_stage: When list_channels runs, the callback extracts and caches the primary channel ID into tool_context.state["buffer_channel_id"].
  • Defensive Injection in _delay_buffer_post: If create_post is dispatched without channelId, the hook automatically injects the cached ID: 
    if tool.name == "create_post":
    if not args.get("channelId") and tool_context:
        cached_channel = tool_context.state.get("buffer_channel_id")
        if cached_channel:
            args["channelId"] = cached_channel
            log.info("Auto-populated channelId for Buffer create_post: %s", cached_channel)
Core Architecture

Preserving the POST_VIA=auto Architectural Innovation

System Design
⚖️ The Lab 1 Upstream Workaround vs. Production Routing

In the upstream Lab 1 curriculum (docs/lab-1-build.html#step-7), the guide advises:

"With both LinkedIn's tool and a real Buffer key active together, every turn fails: 'Duplicate function declaration found: create_post'... Leave POST_VIA blank only if BUFFER_API_KEY is also blank; otherwise set it to buffer or linkedin explicitly in .env."

As documented in Learning 1, setting POST_VIA=buffer or linkedin is an isolating workaround that turns off multi-platform capability. In our architecture:

  • We applied tool_name_prefix="linkedin" to the LinkedIn FastMCP toolsets, producing linkedin_create_post and linkedin_get_profile.
  • Buffer's remote MCP tools remain unprefixed (create_post, list_channels, get_account).
  • With zero namespace collisions, POST_VIA=auto enables the orchestrator to route indifferently based on user intent (immediate LinkedIn post vs. scheduling via Buffer).

Decision: POST_VIA=auto is maintained as an invariant baseline.
