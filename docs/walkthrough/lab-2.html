Prerequisites

Step 2 of 9

Deploy to Agent Runtime (One Command)

Agent Runtime
🎯 1. Concept & Architecture

Deploy the agent to Google Cloud Agent Runtime using agents-cli deploy. Crucial configuration choices:

  • -d agent_runtime: Required because the project was composed by hand without an agents-cli-manifest.yaml.
  • --region us-central1: Deliberately chosen because the Govern pillar's Semantic Governance Policy Engine is regional and requires the agent to reside in us-central1.
  • --agent-identity: Automatically provisions a dedicated cryptographic principal (principal://agents.global...) decoupled from human credentials.
  • --no-wait: Decouples terminal timeout from the 5–10 minute cloud container build process.
💻 2. Execution Command
# Deploy Social Spark to Agent Runtime in us-central1 with dedicated agent identity
agents-cli deploy -d agent_runtime \
  --project $GOOGLE_CLOUD_PROJECT \
  --region us-central1 \
  --agent-identity \
  --service-name social-spark-poster \
  --update-env-vars "POST_VIA=linkedin,DRY_RUN=true,RESEARCH_MODEL=gemini-2.5-flash,DRAFT_MODEL=gemini-2.5-flash,ORCHESTRATOR_MODEL=gemini-2.5-flash,GCS_BUCKET_NAME=lab2-bucket-$GOOGLE_CLOUD_PROJECT" \
  --no-confirm-project --no-wait

# Monitor deployment status
agents-cli deploy --status -d agent_runtime \
  --project $GOOGLE_CLOUD_PROJECT --region us-central1 --no-confirm-project
📸 3. Visual Evidence
✅ Step 2 Checkpoint: Agent Runtime Deployment

Requirement: agents-cli deploy --list --project YOUR_PROJECT --no-confirm-project shows social-spark-poster in us-central1, and the agent appears in the console under Agent Engine with an identity principal against it. Running ./gcp-setup.sh again ends with Done.

Fulfillment: Verified in Figure 2.1. social-spark-poster successfully deployed to Agent Runtime in us-central1 as Reasoning Engine 3820247796918517760, bound to dedicated Agent Identity principal serviceAccount:social-spark-identity@.... Step 3 of 9

Talk to the Deployed Agent (The /api Passthrough)

API Passthrough
🎯 1. Concept & Architecture

Agent Runtime exposes containerized HTTP routes under a managed /api prefix: 

https://us-central1-aiplatform.googleapis.com/reasoningEngines/v1/projects/{PROJECT}/locations/us-central1/reasoningEngines/{ENGINE_ID}/api/{container_path}

Because our container serves FastAPI (`backend/main.py`), mounting AG-UI at `/api/adk`, the deployed engine speaks AG-UI at `.../api/api/adk` without needing any translation bridge.

💻 2. Execution Command
TOK=$(gcloud auth print-access-token)
BASE="https://us-central1-aiplatform.googleapis.com/reasoningEngines/v1/projects/$PROJECT_NUMBER/locations/us-central1/reasoningEngines/$ENGINE_ID/api"

# Inspect OpenAPI documentation from the live container
curl -s -H "Authorization: Bearer $TOK" "$BASE/openapi.json" | head -c 200

✅ Step 3 Checkpoint: Reasoning Engine Passthrough

Step 4 of 9

Sessions that Survive Scale-to-Zero

State Management
🎯 1. Concept & Architecture

By default, ag_ui_adk uses InMemorySessionService, which loses all conversation history when serverless containers scale to zero. To ensure true durability, backend/main.py switches dynamically to Vertex AI Session Service when running on Agent Runtime.

💻 2. Verification Command
# Query active managed sessions from Vertex AI
curl -s -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  "https://us-central1-aiplatform.googleapis.com/v1/projects/$GOOGLE_CLOUD_PROJECT/locations/us-central1/reasoningEngines/$ENGINE_ID/sessions" \
  | python3 -m json.tool
📸 3. Visual Evidence: Streaming Adk Event & Durable Sessions
✅ Step 4 Checkpoint: Durable Sessions

Requirement: Send a message, then list sessions: yours is there, with your user id against it. Send a second message on the same threadId from a fresh process and the agent still has the context. The real proof: come back after the engine has scaled to zero and the conversation is still there.

Fulfillment: Verified in Figure 4.1. The sessions API confirmed persistent thread storage under user devcamp-user. A second message sent on the same session restored full context after a scale-to-zero cold start. (See Learning 9 on surviving scale-to-zero container evictions).

Step 5 of 9

Memory Bank: Cross-Session Intelligence

Memory Bank
🎯 1. Concept & Architecture

While Sessions remember a single conversation, Memory Bank remembers user preferences across conversations. We configure VertexAiMemoryBankService with custom topics (USER_PREFERENCES, EXPLICIT_INSTRUCTIONS, posting_style) and a 90-day TTL.

💻 2. Synchronous Post-Turn Distillation Callback
# backend/social_poster/agent.py
# Wires memory extraction directly into the post-turn callback
# Guarantees execution before scale-to-zero terminates container
async def post_turn_callback(callback_context: CallbackContext) -> None:
    if use_memory_bank and callback_context.state.get("pipeline_stage") == "posted":
        if callback_context.state.get("memory_ingested"):
            return
        await callback_context.add_session_to_memory()
        callback_context.state["memory_ingested"] = True
📸 3. Visual Evidence: Memory Bank & Session Continuity
✅ Step 5 Checkpoint: Memory Bank Extraction & Recall

Requirement: Tell the agent a preference ("I always sign off with Building in public. and never use more than two hashtags"), then publish a post in that same conversation. List memories on the engine; the preference is there as a distilled fact. Now start a brand new conversation and ask for a post on any topic: it should call load_memory and apply the preference without being told.

Fulfillment: Verified in Figure 5.1. Session preferences were distilled by Vertex AI Memory Bank and retrieved in subsequent sessions via load_memory without user re-prompting.

Step 7 of 9

Deploy the Frontend to Cloud Run

Cloud Run
🎯 1. Concept & Architecture

Deploy the Next.js frontend to Google Cloud Run under a dedicated service account (social-spark-frontend). The Cloud Run instance is kept private (--no-allow-unauthenticated), reached securely via gcloud run services proxy on port 8090.

💻 2. Execution Commands
# Build and deploy frontend to Cloud Run
gcloud run deploy social-spark-frontend --source frontend \
  --region=us-central1 --project=$GOOGLE_CLOUD_PROJECT \
  --service-account=social-spark-frontend@$GOOGLE_CLOUD_PROJECT.iam.gserviceaccount.com \
  --no-allow-unauthenticated \
  --set-env-vars="ADK_BACKEND_ORIGIN=https://us-central1-aiplatform.googleapis.com/reasoningEngines/v1/projects/$PROJECT_NUMBER/locations/us-central1/reasoningEngines/$ENGINE_ID/api" \
  --port=8080 --memory=1Gi --min-instances=0 --max-instances=3

# Access private Cloud Run service securely via local proxy
gcloud run services proxy social-spark-frontend \
  --region us-central1 --project $GOOGLE_CLOUD_PROJECT --port 8090
📸 3. Visual Evidence
✅ Step 7 Checkpoint: Cloud Run Private Ingress & Proxy

Requirement: Hitting the Cloud Run URL directly returns 403. Through the proxy, the app loads and completes a full post against your deployed agent. Both halves are now in the cloud.

Fulfillment: Verified in Figure 7.1. Direct unauthenticated access to the Cloud Run service URL was rejected with HTTP 403 Forbidden. Connecting through the local proxy tunnel (localhost:8090) allowed authorized access, driving the cloud-hosted UI end-to-end.

Tear it down (Cost Hygiene)

Cost Hygiene
🎯 1. Concept & Commands

Verify that resources can be deleted cleanly to avoid lingering cloud spend. While serverless containers scale to zero, deleting unused endpoints is standard engineering hygiene.

💻 2. Execution Commands

  --project $GOOGLE_CLOUD_PROJECT --region us-central1 --no-confirm-project

  --region us-central1 --project $GOOGLE_CLOUD_PROJECT --quiet
