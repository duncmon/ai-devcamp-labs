✅ Step 3 Checkpoint: Guardrail Enforcement vs. Model Declines

Requirement: Success is our friendly refusal ("flagged by our content safety checks"). If you get a normal-sounding Gemini refusal instead, Model Armor did not fire: the model just declined. You must prove the distinction.

Fulfillment: Verified in Figure 3.1. When Model Armor is active, adversarial prompts are intercepted before reaching the LLM and emit our friendly refusal. When disabled (MODEL_ARMOR_TEMPLATE_ID=off), automated governance evals fail immediately:

Architectural Distinction:

  • Why Model Armor refusal is superior: When Gemini declines natively (e.g., "I cannot fulfill this request as a helpful language model"), the rejection is probabilistic, prompt-dependent, and prone to jailbreak circumvention. Furthermore, full prompt token costs and model execution latency are incurred before the refusal is generated.
  • Deterministic Contract: Model Armor intercepts the prompt before it reaches the model context window. It returns our uniform, auditable application response: "I can't help with that request — it was flagged by our content safety checks."
  • Evaluation Verification: The governance eval suite (evals/governance.json) specifically asserts equality against our exact refusal string. When MODEL_ARMOR_TEMPLATE_ID=off, the eval score drops to 0% (FAILED), proving that relying on the foundation model alone fails automated governance compliance.
Step 4

Boundary PII Redaction with Cloud DLP

Data Privacy
🎯 1. Objective & Architecture

Implement boundary data sanitization using Google Cloud Sensitive Data Protection (Cloud DLP). Rather than trusting the model to invoke a redaction tool post-facto, an inbound HTTP middleware (backend/pii_middleware.py) scrubs names, emails, and phone numbers at the application perimeter before payloads are committed to session storage or model context.

💻 2. Execution Commands

# Test domestic and international redaction across jurisdictions
uv run python backend/pii_middleware.py --test-international

# Inspect execution traces in Google Cloud Console
# Vertex AI Studio > Reasoning Engines > social-spark-poster > Traces
📸 3. Visual Evidence
✅ Step 4 Checkpoint: PII Redaction & Over-Scrubbing Analysis

Requirement: The draft has personal details replaced by their types. Note whether Cloud DLP also scrubbed anything that was not really personal, and explain why that is expected in boundary governance.

Fulfillment: Verified in Figures 4.1 & 4.2. Inbound HTTP middleware redacts names, emails, and phone numbers in 175ms prior to model ingestion.

1. Observed Over-Scrubbing:

  • During testing, Cloud DLP sanitized non-personal numeric sequences (such as product model numbers ZX-4900-881, internal ticket codes, and software version numbers) and classified them as [PHONE_NUMBER].

2. Why Over-Scrubbing is Expected and Desirable:

  • High-Recall Boundary Strategy: Cloud DLP relies on probabilistic pattern recognition (regular expressions, checksums, and surrounding context dictionaries). In boundary data governance, the operational priority is maximizing recall (zero PII leaks into persistent logs/memory) over precision. A false positive (redacting an internal sku) causes minor phrasing awkwardness; a false negative (persisting a customer's phone number or medical ID in the vector session database) is a GDPR violation.
  • Boundary vs. In-Model Tool Call: Inbound middleware guarantees redaction before persistence. If PII redaction were left to an LLM tool call, the model context and session store would already contain the unredacted plaintext, exposing it to prompt injection extraction. (See Learning 15 for custom regex detectors and Learning 16 on syntactic redaction vs. semantic context).

# Perform semantic vector discovery against registered MCP toolsets
uv run python backend/governance.py registry-search "bigquery"
📸 3. Visual Evidence
✅ Step 5 Checkpoint: Registry vs. Static Wiki Page (50-Agent Fleet)

Requirement: Explain what an Agent Registry gives a company with fifty agents that a static wiki page does not.

Fulfillment: Verified in Figure 5.1. Dynamic registry query and vector search retrieve real-time MCP schemas (e.g., BigQuery MCP with 9 tools) bound to authenticated Agent Identity. For an enterprise operating 50+ autonomous agents, static documentation (Notion, Confluence, Wiki) suffers from catastrophic operational failure. An Agent Registry provides six critical capabilities:

  1. Programmatic Vector Discovery: Orchestrator agents cannot parse human markdown tables. The Registry provides a real-time semantic API (/mcpServers:search) allowing agents to dynamically query: "Find me tools that analyze customer retention data" and receive machine-executable MCP tool schemas at runtime.
  2. Zero Documentation Drift (Live State): Wiki pages decay into technical debt within weeks of deployment. The Registry binds directly to active Reasoning Engine endpoints and Cloud Run instances, reflecting live health, versioning, and availability.
  3. Strict Schema Contracts & Versioning: When an upstream tool updates its parameter requirements, the Registry publishes explicit, validated JSON schemas, preventing breaking changes across consuming agents.
  4. Centralized RBAC & Policy Enforcement: Security teams can enforce uniform guardrails across all 50 agents (e.g. restricting write-access to production databases). A wiki page has zero enforcement capabilities.
  5. Unified Telemetry & Dependency Mapping: All discovery queries, tool callouts, and security violations are linked to the registered Agent Identity across Cloud Logging, Cloud Trace, and Google Cloud Security Command Center.
  6. Cryptographic Identity Verification: A wiki page can be edited by any human user. The Registry validates agents via workload identity federation principals (principal://agents.global...). (See Learning 18 for the detailed architectural comparison between Agent Registry and static wikis).

✅ Step 6 Checkpoint: Policy Existence vs. Runtime Enforcement

Requirement: Show that the policy exists and is bound to your agent, and explain that if you ask the agent to post without approval, what stops it is the approval gate (require_confirmation), not the policy.

Fulfillment: Verified in Figures 6.1 & 6.2. The policy no-unapproved-posts is bound to social-spark-poster in Cloud Console. However, in-flight enforcement occurs via ADK application gating:

Crucial Architectural Distinction (Existence != Enforcement):

  • What the policy establishes: The policy registers a cloud-managed, audited semantic rule bound to the agent's cryptographic workload identity principal in Google Cloud IAM.
  • What actually blocks unapproved posts today: If an attacker instructs the agent to bypass human review, the action is blocked by the application code approval gate (require_confirmation=True in ADK), which generates an adk_request_confirmation signal requiring human interaction.
  • Why the policy does not actively enforce yet: Live runtime policy enforcement by the Semantic Governance Engine requires a dedicated enterprise network harness: an Agent Gateway with client-to-agent ingress routing, a dedicated VPC network with Private Service Connect (PSC), and an authorization extension intercepting Gemini :generateContent API calls. Conflating policy existence with runtime enforcement is a major trap in AI governance; existence establishes intent and auditability, but enforcement requires network interception. (Detailed architectural breakdown in Learning 19).

✅ Step 7 Checkpoint: Gateway Protected Routes & The 8MB Quota Fix

Requirement: The gateway, extension, and policy exist; agentGatewayConfig names your gateway; the injection streamQuery returns 403 PERMISSION_DENIED. Identify which app routes the gateway protects and does not protect, and document any quota hurdles resolved.

Fulfillment: Verified in Figure 7.1. Direct streamQuery injection returns HTTP/2 403 Forbidden: Model Armor: Prompt violates content security configurations at the network edge proxy.

1. Routes Protected vs. Not Protected:

  • Protected by Agent Gateway: Standardized agent protocol interfaces: native Vertex AI :streamQuery, Model Context Protocol (MCP) tool traffic, and Agent-to-Agent (A2A) communications. The gateway proxy intercepts requests at the network perimeter and executes the Model Armor Service Extension with failOpen: false, rejecting injections with 403 PERMISSION_DENIED before container initialization.
  • NOT Protected by Agent Gateway: Custom application routes, specifically the web UI's /api/adk Express/FastAPI proxy. The Gateway only governs interfaces it natively mediates. Custom application paths bypass the gateway proxy and enter the agent container directly, relying on in-agent Model Armor callbacks (Defense in Depth).

2. Crucial Operational Discovery: The 8MB Payload Quota Trap:

  • During deployment, agents-cli deploy crashed with 400 INVALID_ARGUMENT: Request payload size exceeds the limit: 8388608 bytes.
  • The Vertex AI Reasoning Engine API enforces a hard 8MB limit on the uploaded source bundle. Because documentation and screenshots in docs/screenshots/ exceeded 11MB, the CLI bundled them into the payload.
  • The Fix: Created a root .gcloudignore excluding docs/, frontend/, and image assets. This reduced the deployment archive to <50KB, ensuring instant, reproducible deployments.
