OpenTelemetry Context Detachment, Franken-Traces & The Online Evaluation Blind Spot

An empirical autopsy of Python contextvars scoping failures in asynchronous streaming architectures, the generation of conjoined multi-session "Franken-Traces", and their destructive impact on automated production evaluators such as Vertex AI Online Evaluation.

The Instructor's Unanswered Question: In Step 5 of the official curriculum, the instructor noted: "Failed to detach context appears at ERROR for each request once telemetry is on... Open question we did not answer: whether those mis-parented spans affect anything that reads traces by conversation, such as Online Evaluation." This annexe provides the definitive empirical answer, reproducing the exact failure mode in isolation and evaluating its architectural hazards.
Part 1

The Root Mechanism: Asynchronous Contextvars Scoping

SDK Diagnostic

To understand why Failed to detach context appears in Cloud Logging, we audited the interaction between Google ADK's streaming runner and OpenTelemetry's Python SDK:

1. The Contextvars Token Contract

OpenTelemetry Python manages span activation via Python's built-in contextvars library. When a span begins, trace.context_api.attach(context) invokes ContextVar.set(), returning an opaque Token:

opentelemetry/context/contextvars_context.py
def attach(self, context: Context) -> object:
    return self._current_context.set(context)

def detach(self, token: object) -> None:
    self._current_context.reset(token)  # <-- The Crash Site

Python's contextvars specification imposes a strict invariant: a token can only be reset within the exact same context (and asyncio Task) where it was created. If reset(token) is called in a different Task context, the Python interpreter raises:

Interpreter Error
ValueError: <Token var=<ContextVar name='current_context' ...>> was created in a different Context

2. Why Async Streaming Violates Scoping

In Google ADK and FastAPI/ASGI streaming architectures:

  1. Span Activation: The HTTP handler starts an asynchronous generator (e.g. run_async()), entering an OTel span inside Task A and attaching the token.
  2. Cross-Task Event Streaming: Tokens and state chunks are yielded across event-loop cycles as server-sent events (SSE).
  3. Background Cleanup: When the client disconnects or the generator completes, cleanup routines, garbage collection, and span finalization run in a background event-loop task (Task B).
  4. The Detachment Failure: Task B calls trace.context_api.detach(token). Python rejects the cross-task token reset with ValueError. OTel catches the error, leaves the span context un-reset, and logs:
    ERROR: opentelemetry.trace: Failed to detach context

The "Franken-Trace" Disaster:

Because reset(token) failed, Alice's span was never cleared from the worker's contextvar. When Bob's turn arrived at the same worker thread, tracer.start_span() inspected the active context, discovered Alice's active span, and assigned Bob's turn as a child of Alice's span within Alice's trace ID.

Part 3

Destructive Impact on Online Evaluation & Session Analytics

Enterprise Risk

We can now answer the instructor's open question with empirical certainty:

1. Does it affect Cloud Trace & BigQuery? (Safe)

No. In Cloud Trace and BigQuery Agent Analytics, individual spans are serialized with explicitly stamped header IDs (trace_id and span_id) at creation time. The visual waterfall and BigQuery event rows assemble accurately within single isolated invocations.

2. Does it affect Online Evaluation? (Critically Vulnerable)

YES. Automated online evaluation services (such as Vertex AI Online Evaluation, continuous LLM judges, or custom tracing evaluators) ingest production telemetry grouped by conversational session tree. Franken-traces introduce three catastrophic failure modes:

Failure Vector Underlying Mechanism Impact on Online Evaluation
1. Cross-Session Context Bleed ("Franken-Traces") Leaked context causes Turn N+1 (User Bob) to be parented under Turn N (User Alice). The automated judge evaluates Bob's prompt against Alice's conversational context, scoring semantic coherence at 0.0 (Hallucination / Topic Drift) when the agent was completely coherent.
2. Sub-Agent Session Blind Spots AgentTool launches draft_agent in an isolated session ID. If context propagation breaks across the sub-agent boundary, traces fragment. Online Evaluators assessing the root conversation trace see only the orchestrator's high-level delegation, completely missing drafting hallucinations, skill skipping, or sub-agent safety violations.
3. Evaluation Trigger Suppression Automated evaluators trigger scoring when a trace closes cleanly with STATUS_OK. An unhandled ERROR traceback aborts the pipeline. Valid, successful conversational turns are misclassified as server failures and silently dropped from production evaluation datasets, biasing quality metrics.

The Deployed BigQuery Ingestion Audit (The Missing IAM Role)

Empirical Audit

In the instructor's private demo script (docs/instructor/lab-4-demo-script.md), they made a striking admission:

To uncover why the instructor could not demonstrate deployed BigQuery rows, we audited our deployed Reasoning Engine (Engine ID 1836136314752204800). After executing our deployed turn via streamQuery, we queried the row count of agent_events:

Root Cause: Missing Dataset Grants on the Agent Identity

In Lab 2, gcp-setup.sh provisioned the agent's dedicated cryptographic identity (principal://agents.global.proj-498585195540...) and granted it:

  • roles/logging.logWriter (Cloud Logging)
  • roles/cloudtrace.agent (Cloud Trace)
  • roles/storage.objectUser (Cloud Storage)

However, roles/bigquery.dataEditor was never granted to the Agent Identity principal on the agent_analytics dataset. When the deployed engine's BigQueryAgentAnalyticsPlugin attempted to stream rows via the Storage Write API, the call was denied by IAM. Because the plugin swallows write errors to prevent disrupting user-facing chat traffic, the failure was silent.

The Resolution & 91-Row Empirical Proof

Using the official Google Cloud IAM skill pattern, we granted roles/bigquery.dataEditor and roles/bigquery.jobUser to the project-wide Agent Identity principalSet:

Terminal (IAM Binding)
PROJECT_NUMBER=$(gcloud projects describe "$GOOGLE_CLOUD_PROJECT" --format='value(projectNumber)')
PRINCIPAL_SET="principalSet://agents.global.proj-$PROJECT_NUMBER.system.id.goog/attribute.platformContainer/aiplatform/projects/$PROJECT_NUMBER"

gcloud projects add-iam-policy-binding "$GOOGLE_CLOUD_PROJECT" \
  --member="$PRINCIPAL_SET" \
  --role="roles/bigquery.dataEditor" \
  --condition=None

gcloud projects add-iam-policy-binding "$GOOGLE_CLOUD_PROJECT" \
  --member="$PRINCIPAL_SET" \
  --role="roles/bigquery.jobUser" \
  --condition=None

Part 5

Production Architectural Remediation Patterns

Production Best Practices

To safely deploy OpenTelemetry tracing and Vertex AI Online Evaluation in enterprise ADK architectures, teams must apply two architectural patterns:

Pattern 1: Explicit Context Resetting ASGI Middleware

Because generator cleanup tasks cannot reliably reset tokens across asyncio tasks, the outer HTTP/ASGI boundary must explicitly snapshot and restore the contextvar state before and after each request:

backend/telemetry_middleware.py
import contextvars
from starlette.middleware.base import BaseHTTPMiddleware

class IsolatedTelemetryContextMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        # Create an isolated copy of current contextvars
        ctx = contextvars.copy_context()
        # Execute the entire request lifecycle inside the isolated copy
        response = await ctx.run(call_next, request)
        return response

Using copy_context().run() guarantees that any token leaks or context detach failures remain contained within that single HTTP request and never bleed into subsequent turns handled by the same event-loop worker.

Pattern 2: Grant BigQuery Data Editor to Agent Identity

To enable deployed Reasoning Engines to write to BigQuery Agent Analytics, bind roles/bigquery.dataEditor to the Agent Engine principalSet:

Terminal (One-Time IAM Setup)
gcloud projects add-iam-policy-binding $GOOGLE_CLOUD_PROJECT \
  --member="principalSet://iam.googleapis.com/projects/$PROJECT_NUMBER/locations/global/workloadIdentityPools/agents.global.proj-$PROJECT_NUMBER.system.id.goog/attribute.engine_id/YOUR_ENGINE_ID" \
  --role="roles/bigquery.dataEditor"
